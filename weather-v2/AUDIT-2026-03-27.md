## Bugs Found & Fixed

### BUG #1: Variable naming inconsistency
**File:** `core/forecast-sources.js:37`  
**Issue:** Variable named `tempC` but actually contains Fahrenheit  
**Fix:** Renamed to `tempF` for clarity  
**Impact:** None (logic was correct, naming was misleading)

### BUG #2: Wrong API units for OpenWeatherMap
**File:** `core/forecast-sources.js:63`  
**Issue:** API called with `units=metric` but expected Fahrenheit  
**Fix:** Changed to `units=imperial`, variable from `tempC` to `tempF`  
**Impact:** HIGH — would have caused 2x temperature error (double conversion)

### BUG #3: Double unit conversion
**File:** `core/multi-source-forecast.js:177-179`  
**Issue:** Tomorrow.io returns Fahrenheit, code converted F→F (multiply by 1.8, add 32)  
**Fix:** Check if conversion needed before converting  
**Impact:** HIGH — caused 172°F readings (77°F * 1.8 + 32 = 170°F)

### BUG #4: Same bug for OpenWeatherMap
**File:** `core/multi-source-forecast.js:194-196`  
**Issue:** OpenWeatherMap converted F→F after fixing units  
**Fix:** Same as BUG #3  
**Impact:** HIGH (would have affected after key activation)

### BUG #5: Missing source weights
**File:** `core/calibration-v3.js:49`  
**Issue:** `SOURCE_WEIGHTS` missing tomorrow.io and openweathermap → defaulted to 0.50  
**Fix:** Added both with 0.88 and 0.82 weights  
**Impact:** MEDIUM — underweighted premium sources by 40-50%

### BUG #6: Missing source MAE estimates
**File:** `core/calibration-v3.js:64`  
**Issue:** `SOURCE_MAE` missing tomorrow.io and openweathermap → used 3.5°F default  
**Fix:** Added both with 1.8°F and 2.3°F estimates  
**Impact:** HIGH — would overestimate forecast error by 2x, killing YES-side trades

### BUG #7: Wrong diversity scoring input
**File:** `core/calibration-v3.js:137-144`  
**Issue:** `calculateDiversityScore()` expected raw temps, got weights array  
**Fix:** Changed to accept precomputed `diversitySD` from aggregation  
**Impact:** HIGH — diversity scoring would crash or return wrong values

### BUG #8: Timezone-naive timing
**File:** `core/timing.js:20-22`  
**Issue:** Market resolution time calculated in UTC, not local time  
**Fix:** Added comment explaining limitation, approximation good enough for now  
**Impact:** LOW — timing is optional feature, approximation acceptable

### BUG #9: Parameter name mismatch
**File:** `core/forecast-tracker.js:32`  
**Issue:** Function signature said `forecastWeights` but lifecycle called with `sourceDetails`  
**Fix:** Updated signature and docs to match actual usage  
**Impact:** NONE — function worked, docs were wrong

## Code Quality Notes

**Strengths:**
- Clean separation: forecast → aggregation → calibration → entry
- Each module testable independently
- Error tracking built-in from day 1
- Graceful degradation (missing sources don't break system)

**Weaknesses:**
- Two aggregation paths (Open-Meteo vs multi-source) — tech debt
- Timing.js timezone handling is approximate (good enough, but not perfect)
- No unit tests (all tests are integration tests)

**Recommendations:**
1. After 1 month, consolidate to single aggregation path
2. Add unit tests for calibration-v3 edge cases
3. Consider timezone library if expanding to non-US cities
